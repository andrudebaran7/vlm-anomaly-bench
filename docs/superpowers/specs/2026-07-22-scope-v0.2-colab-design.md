# Design — Scope v0.2: MVTec AD 2 under a Colab-T4 compute budget

**Date:** 2026-07-22
**Status:** approved, pending implementation plan
**Supersedes assumptions in:** `docs/protocol.md` v0.1, `docs/datasets-access.md`, `README.md`,
and `OUTLINE.md` in the companion `vlm-anomaly-paper` repository.

## Why this document exists

The v0.1 protocol was frozen on 2026-07-11 before any dataset was downloaded and before a compute
platform was chosen. Three of its assumptions turned out to be false. This document records the
corrections and the resulting scope, so the amendment is dated and visible rather than silent.

### What was wrong

1. **Real-IAD was assumed to be application-gated.** It is not. The dataset is publicly accessible
   on Hugging Face (`Real-IAD/Real-IAD`, research-use-only terms). The "long pole" that
   `datasets-access.md` was built around does not exist.
2. **Real-IAD scale was never checked.** The full release is 622 GB; the downsampled
   `realiad_1024` variant is ~53 GB. Real-IAD Variety (arXiv 2511.00540) is 198,950 images across
   160 categories. None of these fit a Colab workflow.
3. **MVTec AD 2 test ground truth was assumed to be public.** Only part of it is. The test set is
   split into a public part with pixel-precise annotations and a private part whose ground truth is
   withheld; the private part is scored only through the official evaluation server at
   `benchmark.mvtec.com`.

The compute platform is Colab free tier: a single T4 (16 GB VRAM, compute capability 7.5, no native
bf16), with sessions that disconnect at roughly 12 hours.

## Scope

**Primary benchmark:** MVTec AD 2 — 8 scenarios, >8,000 high-resolution images. Evaluated locally on
the public test split, plus one official submission per method to the evaluation server for the
private split.

**Sanity benchmarks:** VisA and MVTec AD (classic), used only to validate our implementations
against published numbers at the ±1.0 I-AUROC tolerance already defined in protocol §2.

**Real-IAD Variety:** removed from the critical path. It becomes an optional extension after M5,
and the paper states the reason explicitly — dataset scale against the available compute budget.
This is a documented limitation, not an omission.

### Consequence for the paper

The title changes to drop the dataset that is no longer in scope:

> *Do Vision-Language Models Survive the Frontier? A Zero-Shot Anomaly Detection Benchmark on
> MVTec AD 2*

Contribution C1 narrows from "both frontier benchmarks" to "MVTec AD 2", and gains something the
original scope did not offer: results on the official public leaderboard. C2 (pre-registered
protocol) and C3 (practitioner guidance) are unchanged. `OUTLINE.md` §4 loses Table 3 (Real-IAD
Variety) and Figure 2's degradation waterfall shortens to MVTec AD → MVTec AD 2.

## Methods under the T4 ceiling

| Method | Status on T4 | Constraint |
|---|---|---|
| WinCLIP / WinCLIP+ | fits comfortably | CLIP ViT-B/16+ |
| AnomalyCLIP | fits | CLIP ViT-L/14 |
| AdaCLIP | fits | CLIP ViT-L/14 |
| PatchCore (full-shot anchor) | fits, RAM-bound | greedy coreset selection is host-RAM bound, not VRAM bound |
| SAA+ | fits, time-risk | GroundingDINO + SAM ViT-H fit in VRAM, but are slow on 2K-resolution images |
| MLLM baseline | **requires model change** | see below |

**MLLM decision:** Qwen2.5-VL-7B in fp16 needs ~14 GB for weights alone, before the visual tokens
of a 2K-resolution image. It does not fit. The baseline is fixed to **Qwen2.5-VL-3B-Instruct in
fp16** (~6 GB weights, leaving headroom for visual tokens). All computation is fp16 — the T4's
compute capability 7.5 has no native bf16.

This is a deviation from the method the survey's readers would expect, so it is reported as a stated
limitation in the paper rather than presented as an equivalent substitution: the MLLM row measures a
3B generalist, not a 7B one, and conclusions about "MLLM capability" are scoped accordingly.

`configs/methods/mllm_qwen.yaml` is pinned to this variant, and the fixed structured prompt and
scoring rubric required by protocol §3 stay unchanged.

## Protocol amendments (v0.2)

Each of these becomes a dated Changelog entry in `docs/protocol.md`.

- **§2 — MVTec AD 2 splits.** Record the real split structure: defect-free train and validation
  sets, a public test part with pixel ground truth, and a private test part evaluated only via the
  server. Accuracy metrics reported locally come from the public part; leaderboard numbers come from
  the server.
- **§4 — metric set.** Adopt the official MVTec AD 2 metric set as the server defines it, alongside
  the metrics already listed.
- **§5 — latency.** Accuracy may be computed on Colab with whatever GPU is assigned. The efficiency
  table is measured in M5 in a single session on one rented fixed instance, using MVTec's official
  runtime and memory-footprint utilities. No latency number is ever reported from a Colab session.
- **§7 — evaluation-server policy (new).** **One submission per method, final, no iteration.** The
  private split is a limited, GT-hidden resource; repeated submissions with selection of the best
  result is exactly the "best of N" that §7 already forbids. Each submission is made only after the
  method's configuration is frozen, and the submission date and returned scores are recorded in the
  results directory.
- **`datasets-access.md` — rewrite.** Real-IAD: publicly accessible on Hugging Face, no application,
  with its size recorded as the reason it is out of scope. MVTec AD 2: official download plus
  evaluation-server registration, with the CC BY-NC-SA 4.0 terms noted.

## Execution architecture

All logic lives in `src/vlmab`. The Colab notebook is orchestration only — clone the repository,
fetch data, launch runs — so that nothing is implemented in a cell that cannot be tested locally.

Two constraints that Colab free tier imposes on the design:

- **Checkpointing per (method, scenario) to parquet in Drive.** Twelve-hour disconnections are a
  routine event, not an edge case. A run that cannot resume is a run that never finishes. The runner
  writes each (method, scenario) result as it completes and skips completed pairs on restart.
- **Data on ephemeral disk, not Drive.** MVTec AD 2 is a few GB against a 15 GB shared Drive quota,
  and reading 2K images through Drive is slow. Data is re-fetched per session; only results persist
  to Drive.

Every result row keeps the config hash, seed, and commit already required by the runner contract, and
additionally records the GPU model Colab assigned, so that accuracy runs remain auditable even though
their hardware varies.

## Items to verify at download time

These are unresolved because verifying them requires the data, and protocol §2 explicitly forbids
relying on memory for them. Each has a defined resolution step in M1:

1. **Exact split directory names** — read from the official MVTec AD 2 PyTorch dataset class, not
   from the dataset paper.
2. **Exact official metric names and definitions** — read from the evaluation server's submission
   documentation and the bundled utils README.
3. **Actual download size of MVTec AD 2** — not published on the dataset page; measured on download
   and recorded in `datasets-access.md`.

No loader, metric, or submission-format code is written before these three are resolved.

## Milestone revision

- **M1** — MVTec AD 2 downloaded, the three verification items resolved, protocol v0.2 and the
  access docs corrected, paper retitled.
- **M2** — pixel metrics (AU-PRO, SegF1) implemented and unit-tested; MVTec AD 2 loader; runner with
  checkpointing; PatchCore and WinCLIP reproduce published VisA numbers within ±1 pt.
- **M3** — full grid on MVTec AD 2 public test split.
- **M4** — one evaluation-server submission per method; leaderboard numbers recorded.
- **M5** — efficiency pass on the rented fixed instance; tables and figures frozen.
- **M6** — preprint.

Real-IAD Variety, if it happens at all, is post-M6 and requires a different compute platform.
